# ADR-016: Fork-Gated Availability

## Status

- **Status**: Accepted
- **Date**: 2026-11-05

## Context

An executor line became selectable once the transaction timestamp passed the
`available-after` of its `manifest.json`, and a builtin runner resolved once it
passed the optional `available-after` of its pin in `current.nix`. Both were 1
global date baked into the build, so 2 networks could not activate the same
artifact at different times, and the test suite could not open every gate

## Decision

### Schedule

`support/genvm-chainforks.json`, built into the manager and shipped next to
`genvm-manager.yaml` as a copy the operator may edit and point
`chainforks_path` at, defines named *forks* and, per network, when each
activates:

```json
{
  "forks": {
    "genvm/executor/v0.3": {},
    "genvm/executor/v0.3/stdlib-fix": { "requires": ["genvm/executor/v0.3"], "description": "free text" }
  },
  "networks": {
    "dev": { "forks": { "genvm/executor/v0.3": "always", "genvm/executor/v0.3/stdlib-fix": "always" } },
    "bradbury-phase2": { "forks": { "genvm/executor/v0.3": "2024-09-01T00:00:00Z", "genvm/executor/v0.3/stdlib-fix": "never" } }
  }
}
```

1. Names are `/`-separated segments of `[a-z0-9._-]`, so they need no escaping
   in a comma- or `|`-separated list:
   - `genvm/executor/<line>` — an executor line
   - `genvm/executor/<line>/<name>` — a behaviour change inside a line
   - `genvm/executor/<line>/runners-<batch>` — runners added to a released line
   - `genvm/manager/<name>` — a manager-side change
2. A date is an RFC 3339 timestamp, `always` or `never`. As fork names, `always`
   is in every active set and `never` in none, and neither can be defined
3. Lines are independent: no line fork requires another, so a network can keep
   v0.3 at `never` and still run v0.4. `requires` ties a behaviour or runner
   fork to its own line
4. Validated by `genvm-tool build-manifest` and at manager startup: unknown or
   duplicate keys are rejected; every network schedules exactly the defined
   forks; no fork activates before one it requires, with `always` the earliest
   and `never` the latest; requirements are defined and acyclic; a name
   extending another fork's name requires it
5. Networks shipped: `dev`, every fork `always`, which the test suite runs on;
   `studio`, `bradbury-phase2` and `asimov-phase5`, with the dates the lines'
   `available-after` used to carry

### Artifacts Name a Fork

1. `executors/*/manifest.json` has a required `fork`, copied into the manager's
   `manifest.yaml` and checked against the schedule at build and startup
2. A `current.nix` pin may set `fork`; it defaults to the fork of the line
   declaring the pin
3. A runner hash is visible *iff* at least 1 line declaring it, up to the
   running line, has its fork active. The build writes this per line into
   `all.json` as `forks`, the sorted, `|`-joined forks of every declaration.
   With v0.3 declaring `a:1`, `b:1` and v0.4 declaring `a:2`, `b:1`, v0.4's
   `all.json` holds `a:1` under `genvm/executor/v0.3`, `a:2` under
   `genvm/executor/v0.4` and `b:1` under both. A fork name the schedule does not
   define fails the build

### Manager

1. Config: `default_network`, which must name a network of the schedule, and
   an optional `chainforks_path`. The shipped schedule is built into the
   manager, so deployments that copy config files by name keep working;
   `chainforks_path` replaces it
2. A run request carries an optional `network`, `detect-version` an optional
   `Network` header; absent means `default_network`, unknown fails the run
   before an executor spawns. A delegated call inherits its caller's network
3. The active set is `{fork | date(network, fork) <= timestamp}`, computed per
   run. A line is selectable *iff* its fork is active; patch walk-forward, the
   newest-line fallback and exact version pins are unchanged
4. The executor gets the active set as `genvm run --forks a,b,c`, sorted,
   without the built-ins

### Executor

1. v0.3 and later resolve a runner *iff* any fork of its `all.json` entry is in
   `--forks`, otherwise it fails as a malformed runner. The transaction
   timestamp no longer gates runners
2. v0.2 accepts `--forks` and ignores it
3. A behaviour change inside a line is a check that its fork is in the set, with
   no new runner or line

## Consequences

### Positive

- Each network activates each artifact on its own schedule, without a rebuild
- The test suite opens every gate by running on `dev`
- Behaviour fixes inside a line need no new executor line

### Negative

- A schedule mismatch is silent: 2 validators with different schedule files
  diverge with nothing pointing at the schedule
- An old v0.2 binary rejects `--forks`, so v0.2 needs a release first
- A fork name is written in an executor submodule and defined in the manager's
  file, so a typo surfaces only at the manager build
- An operator who edited the schedule must merge the shipped one on every
  release that adds a fork, or startup fails on the missing entry
- Networks may activate different subsets, so code must hold for every subset
  `requires` allows
- Each behaviour fork check stays in the executor forever, for replay
- An activated fork cannot be withdrawn
- A v0.4 contract depending on a runner only v0.3 declares works where v0.3 is
  enabled and fails as a malformed runner where it is not
- An exact pin of a disabled line runs with none of its own runners visible
- Setting a line to `never` where contracts already target it sends them to the
  newest-line fallback; it is safe only for a line never enabled there

### Neutral

- Real activation dates for each network are an operator input, not a build one

## Alternatives Considered

### Per-Network Builds

Bake one date set per network into the release. It multiplies release assets
and still cannot open every gate for tests without yet another build

### Keep Timestamps, Add Overrides

Keep `available-after` and let the manager override it per network. 2 sources
of truth for the same gate, and runner gating stays inside the executor's
`all.json`, out of the operator's reach
